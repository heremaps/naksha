## Installation and ownership

- JVM bootstrap that permits create/upgrade/override registers scheduling **after** committing the Naksha admin installation. Ordinary attach-only initialization and PLV8 attachment do not configure cluster jobs. Retry safely repairs a missing/changed job without reinstalling the database. A scheduler failure explicitly reports that database initialization already committed.
- `maintenanceJobs` defaults to true. External schedulers/test deployments may explicitly set it false. Missing preload, missing cron package, authentication or permissions are errors when enabled, not silent success. No server reconfiguration/restart or authentication weakening is performed.
- Independent scheduling connections default `maintenanceSslMode=verify-full` with pgJDBC's normal certificate trust configuration; plaintext fallback is not permitted. An explicit `disable` option exists for isolated local fixtures only. This policy concerns the new scheduling connections, not a claim that the existing pooled connection implementation has been TLS-hardened.
- The same configured master endpoint and installer role connect to `cron.database_name`. PostgreSQL must preload pg_cron; cron job authentication/background-worker configuration is an operator prerequisite. Only the designated cron database installs the extension. All Naksha databases in a cluster must use one shared scheduler/maintenance role; the credential-free `naksha~cron` schema marker verifies its ownership. There are no SECURITY DEFINER wrappers or credentials in cron command text/comments.
- Serialized idempotent reconciliation uses pg_cron's schedule/alter APIs; unchanged jobs are not rewritten. Existing unrelated jobs are never adopted or modified. Schedule is `0 */8 * * *`, interpreted in the server's `cron.timezone` (recommend UTC).

## Execution and cleanup

- Each job is named by PostgreSQL database OID and targets that database through `cron.schedule_in_database`. It verifies database OID, admin schema OID, storage identity and installed runtime version before calling the installed shared Kotlin/PLV8 maintainer. A dropped/recreated database or replaced admin schema cannot silently inherit maintenance. Upgrades must reconcile the job; the sweep never upgrades its own runtime.
- Maintenance is bounded by statement/lock timeouts. SQL manual invocation and cron share a nonblocking database-local sweep guard. Live metadata discovery, history-OFF/tombstone skipping, exact physical provenance checks, no-op lock release and DDL only for missing coverage are retained. The existing partition algorithm remains shared Kotlin; the cron commands contain only orchestration.
- One cleanup job runs in the cron database every eight hours. It compares only this scheduler role's marked Naksha job OID/name pairs against `pg_database`, unschedules dropped/renamed/replaced targets, and removes only marked run-history records older than 30 days. It does not open target connections or scan target metadata. Reinstallation reconciles a database renamed by an operator.
- No production physical `DROP DATABASE` API currently exists in Naksha. JVM `PgStorage.removeMaintenanceJob()` provides explicit idempotent pre-drop unscheduling for operator-managed deletion; it never drops data, and ordinary storage shutdown/deleting a storage descriptor does not imply database deletion. Out-of-band DROP DATABASE is covered by the cleanup job, at most eight hours later. A target job cannot execute after its database disappears; the companion job is therefore necessary.
- New collections are initialized synchronously. Write-time coverage checks/provisioning remain, including protection from date boundaries, unusually fast allocation, busy/skipped sweeps and scheduler outages. No claim is made that four future version buckets guarantee eight hours for every allocation rate.

## Runtime discovery and initial results

Actual pg_cron background-worker execution exposed a previously untested JS platform assumption: `inet_server_addr()` is SQL NULL for internal workers, but `Platform.primaryLocalIp()` returned it through a non-null String contract. `NakshaContext` initialization then failed constructing its non-null default application ID. The adapter now explicitly casts real addresses to text and falls back to `plv8` when the address is absent; the atomic reference contract is not weakened. A focused Node regression covers absent and present addresses. TCP-backed PLV8 tests alone had not exposed this case.
